# Windows Portable ZIP Enterprise Pilot Design

**Status:** Approved
**Date:** 2026-07-15
**Branch:** `enterprise-pilot`

## Purpose

Distribute the enterprise Windows desktop pilot as an unsigned x64 ZIP archive that users extract and run without installation. The archive connects only to the configured on-premises OpenAI-compatible API and loopback sidecar services. User settings and DPAPI-protected credentials remain outside the extracted application folder.

This design replaces the NSIS installer, Authenticode signing, company-CA acceptance, reinstall, and uninstall portions of the existing Windows pilot release plan. It does not change the already-approved offline runtime, company LLM, guidance, permission, or renderer network boundaries.

## Decisions

- The accepted release artifact is a Windows x64 ZIP generated by electron-builder's `zip` target.
- The supported build entrypoint is `bun run package:enterprise:win` on a controlled Windows x64 build machine.
- Direct enterprise electron-builder CLI invocation and `--prepackaged` are unsupported operator paths.
- The pilot permits an unsigned executable distributed through a trusted internal channel.
- Every release includes a SHA-256 checksum and machine-readable release metadata.
- Settings and DPAPI-protected credentials remain under `%LOCALAPPDATA%\com.company.opencode.pilot`.
- Projects remain in user-selected directories and are never placed in or deleted with the extracted application folder.
- Automatic updates and `opencode://` protocol registration remain disabled.
- macOS may be used for development and automated source verification, but accepted release ZIPs are produced and smoke-tested on Windows x64.

## Trust Boundary

The pilot trusts the controlled Windows build account, the fixed package script, and the internal distribution channel. It does not attempt to defend against a trusted build operator intentionally bypassing the package script with arbitrary electron-builder CLI options.

The release boundary instead requires:

1. A clean reviewed source revision.
2. The fixed `package:enterprise:win` command.
3. Package-content verification.
4. A recorded SHA-256 checksum.
5. Windows smoke testing with public internet access blocked.

Unsigned distribution does not provide publisher identity or tamper resistance by itself. The checksum and trusted delivery channel are therefore mandatory, not optional documentation.

## Build Architecture

### Enterprise builder configuration

The enterprise branch of `electron-builder.config.ts` produces:

- `appId`: `com.company.opencode.pilot`
- `productName`: `Company OpenCode Pilot`
- Windows target: `zip`
- Architecture: x64, selected by the package runner
- Artifact: `company-opencode-pilot-${version}-win-x64.zip`
- No `publish` configuration
- No protocol registration
- No NSIS configuration in the effective enterprise target
- No PFX, `CSC_LINK`, `CSC_KEY_PASSWORD`, certificate staging, or custom signing callback

The official runner removes inherited `CSC_*` and `WIN_CSC_*` signing variables from the build and packaging child environments. This keeps the accepted pilot artifact deterministically unsigned and prevents a build-machine profile from enabling signing accidentally. A future signed release requires a separate approved signing design.

Ordinary dev, beta, and production OpenCode packaging remains unchanged.

### Supported package flow

`bun run package:enterprise:win` performs these steps in order:

1. Reject non-Windows or non-x64 hosts.
2. Validate enterprise model, guide, defaults, and allowed-origin inputs.
3. Run `bun run build` in `packages/desktop`.
4. Run the fixed electron-builder Windows ZIP target for x64.
5. Verify the unpacked package contents.
6. Confirm the expected ZIP exists and contains the verified application tree.
7. Generate the SHA-256 checksum file.
8. Generate release metadata JSON.

The runner stops on the first failure and does not publish or move a partial artifact into the accepted release location.

### Environment validation

Required enterprise inputs are:

- `OPENCODE_ENTERPRISE=1`
- `OPENCODE_ENTERPRISE_BASE_URL`
- `OPENCODE_ENTERPRISE_MODEL_ID`
- `OPENCODE_ENTERPRISE_MODEL_NAME`
- `OPENCODE_ENTERPRISE_ALLOWED_ORIGINS`
- `OPENCODE_ENTERPRISE_DEFAULTS_VERSION`
- `OPENCODE_ENTERPRISE_GUIDE_VERSION`

Signing inputs are neither required nor consumed. URL validation rejects credentials, query strings, fragments, backslashes, ASCII control whitespace, deceptive legacy IPv4 notation, and non-origin entries in the allowed-origin list. The base URL may contain a normal API path such as `/v1`.

## Archive Contract

The ZIP root contains at least:

```text
Company OpenCode Pilot.exe
resources/
  app.asar
  enterprise/
    opencode.jsonc
    company-guide.md
    models.json
  licenses/
    OpenCode-LICENSE
```

The verifier checks names and semantic contents rather than accepting file existence alone:

- Enterprise defaults contain the `company-llm` provider.
- The guide contains the expected company guide heading and version metadata.
- `models.json` is valid JSON and contains the configured model.
- `app.asar` is present and non-empty.
- The OpenCode license notice is present.
- No installer or uninstaller executable is required.

## Persistent Data

The extracted folder is immutable application content. Runtime state remains in the existing enterprise user-data directory:

```text
%LOCALAPPDATA%\com.company.opencode.pilot
```

This includes settings, window state, and DPAPI-protected LLM credentials. Moving, replacing, or deleting the extracted folder must not delete this directory. Project directories remain independent and must also survive archive replacement or deletion.

The pilot does not provide a settings-removal uninstaller. Operators may document a separate manual data-removal procedure, but the release script must never execute it automatically.

## Integrity Artifacts

Each build produces:

```text
company-opencode-pilot-${version}-win-x64.zip
company-opencode-pilot-${version}-win-x64.zip.sha256
company-opencode-pilot-${version}-win-x64.release.json
```

The checksum file records the archive SHA-256. Release metadata records:

- Application version
- Git commit
- Artifact filename
- SHA-256
- Defaults version
- Guide version
- Model ID
- Target OS and architecture
- Build timestamp in UTC
- Authenticode status observed during acceptance
- Windows acceptance records

The metadata must not contain credentials, API keys, headers, local certificate paths, or the contents of user settings.

## Windows Smoke Verification

The PowerShell smoke script accepts the ZIP, checksum file, allowed LLM host, and sentinel project directory. It performs:

1. SHA-256 verification before extraction.
2. Extraction into a fresh temporary directory.
3. Required package-content checks.
4. Authenticode status capture for the executable.
5. Confirmation that the pilot executable reports `NotSigned`; any other state fails until a separate signing design is approved.
6. Application launch and bounded startup wait.
7. Confirmation that settings and credentials are written only to the enterprise AppData location.
8. Process-tree network inspection during startup, idle, diagnostics, chat, and shutdown.
9. Rejection of destinations other than the configured internal LLM addresses and exact loopback addresses.
10. Re-extraction as a simulated upgrade and confirmation that AppData settings remain available.
11. Deletion of the extracted application directory and confirmation that AppData and the sentinel project remain intact.

The manual acceptance checklist additionally confirms:

- Company guide and guide version display.
- Credential save and restart behavior.
- Basic response, streaming, and tool-call diagnostics.
- Project override to another allowed internal origin.
- Rejection of a public provider origin.
- No OpenCode Console, models.dev, sharing, updater, plugin registry, LSP download, WSL download, changelog, documentation, feedback, icon, or Discord traffic.
- TLS uses the normal Windows trust store with no certificate-bypass option. No private company CA installation is required by this pilot.

## Error Handling

The package command fails with fixed, non-secret diagnostics when:

- The host is not Windows x64.
- Required enterprise inputs are missing or invalid.
- The base URL is outside the declared allowed origins.
- Build or ZIP packaging exits nonzero.
- Required package files or semantic markers are missing.
- The artifact name or architecture is wrong.
- SHA-256 generation or verification fails.
- Release metadata cannot be generated safely.

The smoke script fails when:

- The checksum differs.
- Extraction or launch fails.
- The executable reports an invalid signature state.
- Unexpected public network traffic is observed.
- AppData persistence or project preservation fails.

Failures must not print credentials, API keys, authorization headers, user-data contents, or full secret-bearing URLs.

## Test Strategy

### Package configuration tests

- Enterprise config selects only the Windows ZIP target.
- Artifact identity and versioned filename are stable.
- NSIS, publish, protocol, and signing inputs are absent.
- Ordinary channel configurations are unchanged.

### Runner tests

- Non-Windows and non-x64 hosts fail before spawning.
- Validation occurs before build.
- Build, package, verification, checksum, and metadata steps run in order.
- Every nonzero step stops subsequent work.
- Signing environment variables are stripped from child environments and never serialized.

### Content verifier tests

- A complete unpacked fixture passes.
- Each required file has an independent missing/corrupt failure.
- Defaults, guide, models, archive, and license semantics are checked.
- The verifier never reads user AppData or project contents.

### Windows acceptance

- Run the automated smoke script on clean Windows 10 x64 and Windows 11 x64 VMs.
- Block public internet while allowing the configured internal LLM endpoint.
- Record the release metadata and result for each VM.

## Migration From Current Task 2

The implementation removes the certificate-specific work added during the earlier NSIS design:

- Delete enterprise certificate staging and cleanup modules and tests.
- Remove `CSC_LINK`, `CSC_KEY_PASSWORD`, alternate CSC, and signing-guard requirements.
- Replace enterprise NSIS target and preflight assumptions with ZIP target validation.
- Retain the safe URL validation improvements that apply independently of signing.
- Retain isolated builder-config tests and the fixed package runner boundary.
- Rewrite Windows Tasks 3 and 4 around extraction, checksum, AppData persistence, and directory replacement rather than install, reinstall, uninstall, and Authenticode validity.

## Acceptance Criteria

The portable pilot is accepted when:

- All source tests and package-local typechecks pass.
- A controlled Windows x64 build produces the three integrity artifacts.
- Package verification passes against the actual generated contents.
- SHA-256 verification succeeds after transfer through the internal distribution channel.
- Windows 10 and Windows 11 smoke and manual acceptance records pass.
- Public egress remains absent throughout startup, idle, configuration, chat, and shutdown.
- Replacing or deleting the extracted application folder preserves AppData settings, DPAPI credentials, and user projects.

## Residual Risks

- An unsigned executable may trigger SmartScreen or endpoint-protection warnings. Internal distribution policy must explicitly allow the pilot artifact.
- SHA-256 proves integrity only when the checksum is delivered through a trusted channel.
- Native Windows behavior, endpoint protection, and network observation cannot be fully accepted from macOS tests.
- Hard deletion of `%LOCALAPPDATA%\com.company.opencode.pilot` by a user or administrator removes settings and credentials; this is outside application-folder replacement behavior.
